## 用户选择方案③，真后台已落地

**架构**：零依赖 Node（仅内置模块）单端口服务，SSR + 文件存储。

- `server.js` —— HTTP 路由：SSR 页面、`/api/*`、静态资源、RSS/sitemap/robots。
- `lib/store.js` —— `data/` 目录读写，frontmatter 解析/序列化，原子写入（tmp+rename），版本历史 `data/.history/<slug>/<ISO>__<reason>.md`（保留 40 份），改 slug 时历史目录跟随迁移。
- `lib/markdown.js` —— 自研 Markdown 渲染，先转义 HTML 再拼标签（无 HTML 直通），支持标题/引用/列表/代码块/加粗斜体/链接图片/分隔线。
- `lib/auth.js` —— HMAC 签名 Cookie 会话（12h，无服务端状态，重启不掉线）、timingSafeEqual 比密码、登录限流 6 次锁 10 分钟。
- `lib/render.js` —— 页面模板 + JSON-LD BlogPosting / canonical / OG（服务"被 AI 搜索引擎检索"的目标）。
- `public/assets/site.css` —— 原 kkhome.html 编辑部风格 CSS 原样抽出（纸感底 #f7f3eb、衬线正文、大写字距 eyebrow）+ 详情/笔记/照片/页脚新样式。
- `public/admin.html` —— 后台：登录、文章 CRUD（草稿/标签/实时预览/⌘S/本地草稿兜底/历史版本恢复）、笔记与照片行内编辑、站点设置。
- `tools/smoke-test.js` —— 端到端冒烟测试，起真实子进程打真实 HTTP，61 项断言全绿。

**关键决策与理由**：
- 选 SSR 而非前端渲染 —— 内容必须出现在 HTML 源码里，AI 爬虫与搜索引擎才抓得到。
- 零依赖 —— 服务器上 `node server.js` 就能跑，不用 npm install，不用管依赖安全更新。
- 密码：优先读 `ADMIN_PASSWORD` 环境变量；没有就首次启动生成随机密码写 `data/.admin-password`（避免出现可猜的默认口令）。当前实例用的是生成密码。
- 内容迁移：只搬 kkhome.html 里真实存在的东西。3 篇文章的正文原文里本来就只有摘要，所以标题+摘要原样入库，**没有替用户编正文**。`long-term-rhythm`（原首页置顶卡片）只有标题和一句标语，建为草稿。
- 笔记/照片原文没有日期字段，故留空而**不编造日期**；渲染时空日期不出日期列。
- `/en` 语言开关改为不可点（英文版不存在），避免再造一个死链。

## 用户部署到 101.200.226.187:3000 后登不上后台 → 加诊断能力

用户反馈「http://101.200.226.187:3000/admin 后台登不上」。我够不到那台机器，所以把「看不见的服务器」变成可自证：

- **`GET /api/health`**（免登录）：服务身份、运行时长、Node 版本、data 目录路径与可写性、密码来源（env/file/none）、文章/草稿/笔记/照片计数、当前锁定状态。刻意不含密码本身。
- **`tools/doctor.js`**：服务器本地一键体检。查 Node 版本、关键文件齐全度、data/ 可写性、密码来源与掩码、服务身份（防「端口上跑的是别的服务」，用 `lsof -i :PORT` 提示）、服务侧写权限、锁定状态，然后**用它自己找到的凭据真的 POST 一次登录**并读 bootstrap。分场景给出结论与修复命令，exit 0/1。
- **`tools/set-password.js`**：`node tools/set-password.js 新密码 | --random | --from-file <文件>`。密码按请求实时读，重设后**不用重启**即生效；若环境变量 ADMIN_PASSWORD 存在会明确警告它优先级更高、文件被忽略。
- **登录失败提示改成页面常驻**（原来 2.6 秒的 toast 一闪而过，看起来像「点了没反应」），并按 HTTP 状态给具体指引：401 说密码在哪、429 说重启即可解锁、500 说查 data/ 权限、0 说服务没连上。
- 登录尝试写服务日志：`[login] 失败 <ip>：密码不匹配（校验对象来自 file/env）`、`[login] 成功 <ip>`。
- 启动预检：data/ 不可写时打印醒目警告并说明「站点能看，但登录一定失败、文章一定存不进」。
- **锁定只在内存里** —— 重启进程立即解锁，这一点写进了 429 的响应文案和 doctor 的建议里。

**关键教训**：sandbox 里 `nohup ... &` 起的进程在本次 Bash 调用结束后就被回收，跨调用访问会 ECONNREFUSED。所以所有需要「起服务再打请求」的验证必须写在**同一次** Bash 调用里。

冒烟测试扩到 **77 项全绿**，新增覆盖：health 身份与不泄密、doctor 在健康态与锁定态的判断、密码热更新与旧密码立即失效、连错 5 次仍 401 / 第 6 次告知锁定 / 之后 429、锁定期间正确密码也进不去。

实测四种场景：健康→全绿 exit 0；忘密码→set-password 热生效；端口无服务→ECONNREFUSED + 启动指引；端口被 python http.server 占着→识别出 HTTP 404 非本服务。

## 把 /Users/limohan/Downloads/2048-main 的一堆网页并进站点（实验区 /lab）

来源是 2048 游戏仓库（Gabriele Cirulli，MIT）的 fork，用户在里面加了一批设备能力 Demo。10 个页面性质差很远，先问清三件事再动手，用户选了：独立实验区入口 / 改成本地存储 / 保持各页原样。

**搬进来的 10 个页面**

- 有外部依赖，**全部改成本地**：`markdown`（原拉 marked + github-markdown-css → 改调服务端自己的渲染器）、`note`（留言板，原 Supabase → 本地）、`photo`（相册，原 Supabase Storage → 本地 + 与博客 /photos 共用数据）、`weight`（原 Supabase + Chart.js → 本地 + 手写 SVG 折线图）

**关键决策**
- **入口只挂页脚，不占主导航** —— 用户在「独立实验区」和「混入主导航」之间选了前者，目的是不搅乱刊物的导航结构。
- **三个 Supabase 页面的原始形态有真实风险**：项目地址与 `sb_publishable_...` 密钥明文写在 HTML 里，任何人拿到页面就能读写删你的留言/照片/体重。改成服务端存储后这个暴露面消失，也不再依赖境外服务与外网。
- **权限模型按数据性质分别定**，不是一刀切：留言板公开可读可写（留言板的本质，因此必须限流：同 IP 每分钟 3 条、单条 ≤200 字、总量 ≤500）；相册公开可读、上传删除需登录；体重全程需登录。删除一律需登录。这一点我偏离了之前跟用户口头描述过的「留言接笔记系统」——把访客留言塞进作者自己的笔记库是错的，既会污染作者内容，也等于给公开写权限开了个后门。
- **上传不收 SVG** —— SVG 能内嵌 `<script>`，被当图片直接打开就是任意脚本执行点。只收 PNG/JPEG/GIF/WebP/AVIF。
- **上传不走 multipart**：原始二进制 POST + 文件名放 `X-Photo-Name` 头。服务端不用拼边界、不用引依赖。
- **同一天体重算修正（upsert），不是再加一条** —— 否则手抖点两下提交，折线上就多一个假的坑。
- **顺手修了既有的三处毛病**：`serveStatic` 的前缀判断用 `startsWith(base)` 会让同级目录 `assets-x` 通过（改成 `resolveWithin()` 比对 base + 分隔符）；`options.url` 拼字符串会被 WHATWG 解析器把 `..` 规整掉，导致冒烟测试里那条「拒绝路径穿越」其实**什么都没测**（改成 options 对象直传 path）；留言板原来用 `innerHTML` 拼留言内容，等于让别人往页面里注脚本（改 `textContent`）。
- **camera.html 原来没有 `<head>`、没有 viewport、没处理 `getUserMedia` 失败** —— 用 IP 访问（非安全上下文）时浏览器直接拒绝，页面看起来就像坏了。补了 viewport + `playsinline`（iOS Safari 必须，否则视频全屏接管）+ 明确的失败原因 + 保存按钮。

**踩的坑（都写进 MEMORY.md 了）**
1. 冒烟测试的条数断言写死了 `length === 1`，用户自己记过体重就必然报红 → 全改成相对量。
2. 备份是在 `waitForServer` **之前**读的，那几个 json 由服务启动时创建，于是读到「文件不存在」→ 备份为 null → 什么都没还原。挪到服务起来之后读。
3. 一次被中断的运行会在 `data/articles/` 留下 `smoke-test-*.md`，其中一篇是**已发布**状态，于是之后每次运行的 sitemap 断言都失败 —— 表现像新改坏的。加了开跑前的自家前缀清扫。
4. 跨 Bash 调用把 glob 传给 `rm`，zsh 无匹配会直接报错中止 → 改用 `find ... -delete` 或 `setopt nonomatch`。

**验证**：冒烟测试 77 → **145 项全绿**，连跑 10 次零残留；单独造了一份「用户已有数据」（含当天体重记录）验证跑完三份 JSON 指纹一致、uploads 为空。doctor 新增实验区页面可达性、索引可达性、上传目录可写三项检查。

## 收尾复查：残留会「固化」的坑（已修）

交付前顺手核对数据，发现 `data/lab/messages.json` 里躺着 2 条 `冒烟测试留言`、`data/uploads/` 里躺着 2 个 70 字节的夹具 PNG。之前「连跑 10 次零残留」的结论没错，但**漏掉了一个更隐蔽的情形**：一轮跑漏之后，后面的每一轮都会主动把它保住。

**机制**：备份是在清扫之后、服务启动之后取的。上一轮漏下来的残留已经在文件里了 → 被当成「用户自己的留言/照片」→ 每轮都忠实地还原回去 → 残留永久化。用 md5 对比跑前跑后确认了这一点：`messages.json` 的哈希**一字不差**，说明那一轮既没造新的、也没清旧的。

差集清理（`uploadsBefore.has(name) → continue`）同理：残留进了基线清单，就再也不会被删。

**改法**：新增 `sweepLabArtifacts()`，只删能被证明是测试自己造的东西，且**跑前跑后各扫一遍**。
- 留言：正文匹配 `/^冒烟测试留言/` —— 只可能是测试写的。
- 上传：名字符合 `^\d{8}-[0-9a-f]{12}\.png$` **且**逐字节等于 `TINY_PNG` **且**没有被 `photos.json` 引用。三条同时满足才删；真被引用的（用户自己传的，哪怕内容一样）一律不碰。
- 认不出来的一律保留 —— 宁可漏删，不可误删用户数据。
- 跑前扫保证备份里装的是真数据；跑后再扫兜底，防止把脏东西一代代继承。

受控验证：植入「1 条真留言 + 1 条假留言 + 3 个夹具 PNG + 1 个上一轮遗留 PNG」，跑完报「清理 5 项」，真留言原样保留，uploads 清空。再植入「1 真 + 2 假 + 2 夹具」，结果一致。

**另一个自己踩的坑**：用 `| head -12` 截断冒烟测试输出，会把 node 进程弄成 SIGPIPE 崩溃、`finally` 不执行，子进程服务遗留在测试端口上，下一次跑就 `ECONNREFUSED`。教训 —— **冒烟测试的输出重定向到文件再看，不要接 `head`/`tail` 管道**。
